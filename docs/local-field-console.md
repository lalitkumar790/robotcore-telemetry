# Automatic RobotCore field collection

The field workflow is local-first at the laptop and paired over LoRa. After one-time installation/key provisioning, a normal experiment does not require SSH into the Pi, manually starting cloudflared, copying a tunnel URL, or entering fresh receiver credentials.

## Architecture

1. **Pi service starts at boot.** It discovers GPS USB, LoRa-E5 USB and WT901BLE68 BLE. It checks outbound internet periodically.
2. **Pi tunnel comes online.** When internet is reachable, the Pi starts a temporary Cloudflare Quick Tunnel to its local field-control API on port 8766.
3. **Encrypted LoRa pairing.** The Pi announces the tunnel URL, a short-lived bearer token, device ID and expiry in an AES-GCM encrypted RCP1 packet. The 256-bit pairing key is provisioned once on Pi and laptop. The beacon is re-announced periodically.
4. **Laptop auto-discovers the Pi.** The laptop receiver recognizes RCP1 packets separately from RTP telemetry, authenticates/decrypts them, and publishes the current pairing state through its local bridge.
5. **Dashboard auto-connects.** Open the dashboard served by the laptop at http://<laptop-ip>:8765/. It reads the local bridge bootstrap, sees the encrypted LoRa pairing, and connects to the Pi API without manual tunnel configuration.
6. **Paired capture.** Start/Stop from that dashboard. One generated session ID is passed to Pi and receiver. The Pi RCM, sidecar, manifest and laptop CSV carry that session ID.
7. **Replay and export.** Load the Pi .rcm, its .events.jsonl, and matching laptop CSV in the dual-ended capture section. Analyze alignment, then use Session Replay and Export merged session JSON.

The public Vercel site remains useful for post-run visualization/review, but the **automatic hardware pairing workflow is on the laptop-hosted dashboard**, because the laptop owns the LoRa receiver and the local bridge credentials. A browser opened on the hosted Vercel page cannot directly discover a private USB radio on your laptop.

## One-time Pi installation

Back up existing mission files first. From your existing repository checkout on the Pi:

    cd ~/robotcore-telemetry-field
    git pull --ff-only origin main
    cd hardware/pi-transmitter
    bash install_field_console.sh

The installer:
- installs Pi transmitter and local console dependencies;
- disables the old robotcore-transmitter.service that automatically started recording on boot;
- enables robotcore-field-console.service so the agent starts without a Pi login;
- creates /etc/robotcore-pairing.key (256-bit shared pairing key) and a stable Pi device ID;
- attempts to install the official cloudflared Debian package for the Pi architecture;
- prints the pairing key once for initial laptop provisioning, as well as the local Pi console control token.

Keep the printed pairing key private. It is not the per-run tunnel token. The per-run token is generated by the Pi agent and delivered only inside authenticated encrypted LoRa beacons.

Useful service diagnostics:

    sudo systemctl status robotcore-field-console.service --no-pager
    sudo journalctl -u robotcore-field-console.service -n 100 --no-pager

The Pi service starts the tunnel/beacon agent automatically, but does **not** begin collecting a mission until Start is pressed in the dashboard.

## One-time laptop installation and key provisioning

In Windows PowerShell:

    cd "$HOME\robotcore-telemetry-field"
    git pull --ff-only origin main
    cd hardware/laptop-receiver
    py -m venv .venv
    .\start_field_station.ps1

On first launch, the script installs any missing Python dependencies and asks for the one-time Base64 pairing key printed by the Pi installer. Paste it once. The key is saved under:

    %USERPROFILE%\.robotcore\pairing.key

The script then starts the managed receiver bridge, auto-detects the LoRa-E5 by USB ID 10C4:EA60, and prints the laptop's private-LAN address. Keep the PowerShell window open while collecting data. The script does not start a laptop Cloudflare tunnel.

If Windows Firewall blocks phone access, use an elevated PowerShell window and run:

    cd "$HOME\robotcore-telemetry-field\hardware\laptop-receiver"
    .\setup_field_station_firewall.ps1

The helper creates a TCP 8765 inbound rule for the **Private** Windows network profile only. Do not expose the bridge on a Public network.

## Each field session

1. Connect the Pi to a network with outbound internet. The laptop's Wi-Fi/ethernet must let the phone reach the laptop's local dashboard. The Pi does not need to be on the same subnet as the laptop if its Quick Tunnel is reachable.
2. Open http://<laptop-ip>:8765/ on the laptop or phone. The receiver can show serial/radio health before the Pi has internet.
3. Wait for **Pi discovered · encrypted LoRa pairing received**. The panel reports Pi internet/tunnel status and laptop serial/radio status. If it remains in waiting state, inspect the Pi systemd log and the receiver's pairing counters/errors.
4. Enter an experiment label such as MANIT-20261030-A. Start becomes active only when the pairing is fresh, Pi preflight passes (GPS USB, LoRa-E5 TX, WT901BLE68), and the laptop receiver is connected with radio configuration acknowledged.
5. Press **Start paired recording**. A shared session ID is created. The Pi opens its .rcm, .events.jsonl, .manifest.json; the laptop opens receiver_<experiment>_<session>.csv.
6. Wait for valid packet counters to move at the base station, then walk the route.
7. Press **Stop & save both files**. The Pi is stopped first; the laptop CSV is closed after Pi stop is acknowledged. Preserve all four files together.
8. After Stop, the laptop dashboard automatically downloads the completed Pi .rcm, .events.jsonl, .manifest.json and matching laptop CSV through the authenticated APIs. It verifies that all four artifacts share the same session ID, aligns them by RTP sequence, and prepares Session Replay. Export the merged JSON from the replay panel for archival and later ML work.

USB COM numbers can change. The laptop launcher does not pin COM8; it uses the LoRa-E5 USB ID and retries/re-discovers after a disconnect. A receiver serial open is not the same as successful radio configuration. A TX DONE modem response is not an RX acknowledgement.

## Session pairing and replay semantics

- session_verified=true means the Pi sidecar session ID exactly matches the receiver CSV Field Session ID. Do not train models on a merged export with a mismatched/unverified session until the source files have been checked.
- Pi .rcm packets do not carry per-sample acquisition timestamps. When the .events.jsonl sidecar is present, replay uses sample_recorded.timestamp_unix. Without it, replay is explicitly sample-index based; it does not invent sample timestamps.
- Receiver timestamps are the laptop's packet-receive time, not Pi transmit time. Keep both clocks and time fields distinct.
- The sidecar records skipped GPS-fix samples. These are included as auxiliary events in the merged export but are not added to the transmitted-packet PDR denominator.
- The automatic post-run sync uses short-lived Pi authorization held in browser memory. Raw Pi and laptop files remain on their source devices; the browser downloads temporary file blobs for parsing and does not upload them to Vercel. The merged JSON is downloaded only when the user presses Export.
- RSSI/SNR exist only for received packets. Never fill them for missing packets.

## Network and tunnel limitations

This prototype uses a Cloudflare **Quick Tunnel** on the Pi. Its trycloudflare.com hostname is temporary and changes when the connector restarts; the address works only while the cloudflared process is alive. Quick Tunnels are intended for development/testing, not a reliable production endpoint. The pairing token is encrypted on the LoRa link, but the resulting tunnel is publicly reachable and depends on possession of that token. Do not forward local control ports to the public internet.

For long-running research campaigns, replace Quick Tunnel with a named Cloudflare Tunnel/custom domain or another authenticated stable rendezvous service, and add an explicit offline/stop fallback. The local Pi and laptop files continue to be written on their own devices if the phone loses Wi-Fi, but you may not be able to issue Stop from the UI until the control path recovers.

The phone, if used as the dashboard screen, must be able to reach the laptop's private-LAN address. Some campus Wi-Fi networks block client-to-client traffic. In that case use a private router/hotspot for the laptop and phone. The Pi only needs outbound internet for the current Quick Tunnel prototype.

## Manual recovery

Do not delete a partially completed session. Check Pi state:

    sudo systemctl status robotcore-field-console.service --no-pager
    sudo journalctl -u robotcore-field-console.service -n 160 --no-pager

Keep the laptop field-station window open and inspect its reported last_error, pairing_rejected, serial_connected and radio_configured state. If tunnel pairing is stale, wait for the Pi agent to re-establish internet/tunnel/beacon. Session files are local and should be preserved for later diagnosis.
